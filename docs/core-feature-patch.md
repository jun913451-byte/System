# 核心功能补丁

本补丁记录计划、未预订事项与助手行程投影的当前规则。基础链路已实现，并完成自动化及隔离浏览器核验。

## 后期演示核心

以下两项是 AI 行程助手后期演示的核心能力，记录的是目标范围，不代表所有入口和边界均已完成验收。

- **冲突分类与协同**：每个冲突分别标注严重程度（硬／软）和项目范围（项目内／跨项目）；未关联项目的订单单独处理，不推断归属。交通、酒店、天气、地点是冲突类型，可按判定依据细分，不与上述两个维度混为一类。硬冲突依据确定事实判定；软冲突表达需要留意但尚不能确定的问题。跨项目冲突同步出现在两个受影响项目的对话和提示点，但右上角保持单条通知且共享已读状态。右上角硬冲突通知打开触发订单详情，软冲突通知打开触发项目对话；项目提示点始终打开对应项目对话。
- **未关联项目订单的通知**：硬冲突通知进入订单区、右上角和页面顶部警告，不生成项目对话或项目提示点；软冲突只进入右上角通知，点击打开 AI 行程助手，不推断或新建项目关联。
- **冲突提醒呈现**：同一轮评估发现多个冲突时，合并为一条简洁提醒，列出受影响安排和冲突类型，避免连续发送多条消息。
- **对话中发现冲突**：用户正在某项目对话中提出新安排并触发冲突时，直接在当前回复中说明，不重复弹页面级警告、右上角未读通知或给当前项目增加未读点。硬冲突仍显示在相关订单旁；软冲突只保留在对话中。若跨项目影响另一个项目，另一个项目仍按跨项目规则收到通知。
- **冲突处理入口**：跨项目冲突进入独立的“冲突处理”对话，旁侧行程区域切换为冲突管理；项目内冲突仍在对应项目的普通对话中处理。未关联项目的订单继续从订单详情和右上角通知进入，不推断项目归属。
- **冲突后的对话处理**：助手说明影响并逐项提出建议。行程调整经用户明确同意后应用；订单操作必须先锁定具体订单、操作类型以及改期等目标值，再逐项询问是否同意。用户提出修正时，助手据此重列操作并重新确认。无冲突的行程请求按既定规则直接调整。多笔订单操作每次只执行一项；完成后重新读取订单与行程并评估剩余影响，再提出下一项。助手仅可在冲突处理流程中、得到该项明确确认后更改本地演示订单；不授予创建订单、购买商品或任何真实交易权限。实际供应商办理、支付、费用和退款仍由用户处理。
- **用户暂不回复**：保持当前行程不变，冲突仍未解决；不重复催问。提醒的已读状态与冲突解决状态分开，用户之后可在对话中继续处理。
- **用户知悉但维持原计划**：停止将该提醒作为未读事项提示，保留未解决的冲突记录；用户知悉不等于冲突事实消失。
- **部分处理冲突**：合并提醒中的冲突项独立追踪。用户可以只处理其中一部分；只应用用户明确要求的行程改动，其他未解决冲突继续保留，并在同一条回复中简要列出，不另发提醒。
- **行程内商品入口**：交通、酒店、景点沿用当前行程中的入口；交通票进入对应交通方式、日期、起终点的结果列表，并突出行程中的候选项。助手行程卡片展示一班最符合当日安排的候选，时间适配相同时再参考演示价格，完整班次列表仍可查看。后期演示视频暂定使用杭州到沈阳，保证该路线和演示日期有机票、火车票数据，其他城市覆盖不是本次演示前置要求。缺少对应演示数据时由脚本生成，不由大模型编造，也不代表真实供应。旅游包使用交通、酒店、景点数据组成并打开套餐详情；演示中每个项目至多呈现一个匹配套餐，不做多套餐选择，无匹配时隐藏入口。套餐入口放在每日安排切换栏中、位于第一天之前，但默认仍显示第一天。各入口复用频道已有详情／购买流程；从商品列表或详情返回时恢复原助手项目、选中日期和滚动位置。由助手入口完成购买后停留在成功页，并提供返回行程与查看订单两个操作。

- **未预订事项与行程协同（基础链路已完成）**：明确加入行程的待安排事项保存在 `saved_plans`，可关联或解绑旅行项目。项目删除只解除关联，不删除事项；助手仅将关联内容投影到行程，不回写订单或已保存行程。旧浏览器本地事项会在服务端可用时逐条迁移，失败保留并可重试。商品沿单件详情和购买流程办理，不进入集合结算。
- **订单出行人信息（已完成）**：计划结算与单独购买都从持久化出行人资料中选择具体人员，并在订单中保存下单时的姓名、证件号快照；跨订单冲突只比较实际重合出行人。
- **购买与硬冲突**：发现硬冲突不拦截新订单；照常保存，随后按项目归属展示提醒。进入冲突处理后，助手可按逐笔确认规则修改本地演示订单。
- **AI 行程助手提醒（现有基础已完成；统一处理待开发）**：硬、软冲突均有确定性分类、持久化提醒、已读同步和助手对话记录；目前有行程归属的软冲突从右上角通知打开对应对话，硬冲突从通知打开对应订单。天气提醒与助手回复也进入对应对话。后台定期检查临近旅程的可信天气预报，恶劣天气按项目和日期生成软提醒；预报不可用不推测天气或解除提醒。天气变化不会自动修改已有行程。
- **逐笔订单操作确认（待开发）**：冲突处理的每项提案要绑定单一订单和单一动作；改期必须给出准确目标日期。用户修改目标后废弃旧提案并重新确认。执行后重新获取订单和行程，重新评估后续动作。后端必须校验订单状态、可办理规则和提案内容，不能只依赖前端按钮禁用。
- **交通商品匹配（已完成）**：按行程实际起终点、方向、日期和交通方式匹配商品；目的地内部交通不会误展示无关跨城票。
- **目的地内部交通购票（规则已完成）**：目的地内部短途交通保留为行程安排，不默认触发购票推荐；只有用户明确购票或存在精确路线和日期匹配时提供入口。
- **中转硬冲突判定**：同一出行人的交通时间重叠属于硬冲突；判断短时中转是否为硬冲突，必须有足以识别机场／车站及交通方式的信息。仅有城市级起终点时不得直接判硬冲突，可作为软提醒。同一机场按至少预留 2 小时、同一火车站按至少预留 30 分钟作为课程演示规则；跨枢纽若缺少地面换乘时间数据，不判硬冲突。
- **跨项目冲突检查**：同一出行人的有效订单跨项目比较，项目归属不屏蔽真实时间冲突。由新订单触发的冲突事件归属于新订单所选项目（如有），并指出冲突订单及其项目；未绑定项目时不推断项目归属，按未绑定订单通知规则处理。
- **订单改绑后的提醒归属**：用户在订单详情更改项目关联时，未解决的冲突提醒随订单迁移到新项目通知范围；保持原事件和已读状态，不重复创建事件。
- **冲突解除与列表排序**：订单更改或取消导致硬冲突不再成立时，保留对话历史，将事件标记为已解决并同步清除未读提醒。软冲突仅在新信息能确定其原因已消失时自动解决；状态不明确时保留提醒。未解决冲突排在已解决冲突之前。订单列表中未出行／进行中的订单排在前面，已完成订单排在最底部。
- **软冲突分类**：订单目的地与所关联项目不一致、订单日期超出项目日期范围等“可能不属于该行程”的情况属于软冲突，不与同一出行人确定的时间重叠／过短中转混为硬冲突。

端到端核验覆盖项目归属提醒、已读联动、订单通知与助手对话入口。外部交通延误事件源、真实供应商数据和支付不属于课程原型范围。
