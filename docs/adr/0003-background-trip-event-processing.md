# Process Trip Events in the Background

Trip events and scheduled runs must be processed by the backend without an open browser page, so the assistant can resume work when the traveller is away. The backend is the source of truth for travel projects, itinerary versions, booking references, confirmed travel memory, events, and assistant runs; the frontend submits commands and renders persisted state rather than owning business data in local storage. In this course prototype, only newly created bookings trigger an immediate backend consistency check; booking cancellations, rescheduling, and other status changes are out of scope. Test bookings retain the selected product ID and a booking-time snapshot of relevant route, travel date and times, or hotel stay dates; no real-time inventory is modeled. The result is persisted for later display. An in-process backend handler is sufficient; no external queue or broker is required. The assistant never creates, changes, reschedules, or cancels a booking. When a new booking has no clear conflict, the backend reconciles the itinerary to reflect it; when there is a clear conflict, the assistant warns and asks the traveller before changing the itinerary.
